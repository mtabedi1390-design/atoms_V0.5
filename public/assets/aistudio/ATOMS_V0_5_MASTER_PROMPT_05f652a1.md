# 3. NON-NEGOTIABLE SCIENTIFIC HONESTY

The phrase “visualize all 118 atoms accurately” must be handled with proper atomic-physics distinctions. A neutral many-electron atom does not have one exact, simple hydrogen-like orbital wavefunction. A many-electron ground state is a correlated quantum state; the one-electron density and orbital decompositions depend on the computational method, state, averaging convention, and observable.

The application must never imply that an approximate independent-electron orbital picture is an exact many-electron solution.

## 3.1 Distinguish the following physical objects

The UI and documentation must keep these separate:

1. A one-electron wavefunction `ψ`.
2. A one-electron probability density `|ψ|²`.
3. A radial orbital function `R_nl(r)`.
4. A radial probability distribution `P_r(r) = r² |R_nl(r)|²`.
5. A multi-electron wavefunction or configuration-state function.
6. A one-electron density `ρ(r)` derived from a many-electron state or determinant.
7. A spherical/configuration average of an open-shell density.
8. A visual probability/electron-density sample cloud.
9. A visual scale or nucleus marker used for readability.

Never use “electron orbit” to describe the point cloud. Samples are samples of a probability or density distribution, not classical trajectories or little particles following paths.

## 3.2 Hydrogenic model

The current exact non-relativistic hydrogenic solution is appropriate for a single electron moving in a Coulomb field, such as neutral hydrogen or a genuinely one-electron ion.

For a nuclear charge `Z > 1`, selecting the hydrogenic model represents the corresponding one-electron ion, not the neutral atom. Preserve and strengthen this distinction throughout the UI.

The model must state its assumptions, including where relevant:

- Non-relativistic Schrödinger Hamiltonian.
- Point nucleus.
- Infinite nuclear mass unless reduced-mass correction is explicitly applied.
- No electron-electron interaction because there is only one electron.
- No fine structure, Lamb shift, hyperfine structure, or finite nuclear-size correction unless separately implemented.

The exact hydrogenic radial and angular solutions should remain analytically and numerically validated.

## 3.3 Slater-screened model

Slater's rules may remain as a fast qualitative fallback or educational approximation.

They must not be described as an exact self-consistent atomic calculation, a Hartree–Fock calculation, an experimental orbital energy, or a quantitatively accurate heavy-element wavefunction.

Inspect the use of effective principal quantum number `n*`, `Z_eff`, energies, and radial expectation values for internal consistency. Document exactly which formulas are used and where they are extrapolated.

For elements and properties where this model is the only available option, visibly identify it as a qualitative/approximate fallback. The app may still display an atom, but it must not award it a high-accuracy status.

## 3.4 Hartree–Fock datasets already in the repository

The current bundled PySCF data must be audited at the level of the actual JSON schema and calculation method.

The README describes the current H, He, C, N, O, and Ne datasets as RHF/ROHF with aug-cc-pVTZ, point nucleus, non-relativistic, and no electron correlation.

The exported density is described as a **spherically averaged total electron density**. It is not a subshell-resolved collection of orbitals. Do not display it as though it independently provides accurate 1s, 2s, 2p, etc. orbital wavefunctions.

The existing HF dataset may be used for an appropriately labelled full-atom spherical density visualization after independent validation. Preserve its calculation metadata and limitations.

## 3.5 Open shells and atomic terms

Do not silently assume that every partially occupied subshell has a unique, spherically symmetric orbital arrangement.

For open-shell atoms:

- Use authoritative ground-state term/configuration information where available.
- Distinguish a specific magnetic substate from a statistical/rotational/configuration average.
- Explain when an ensemble or spherical-average convention is used.
- Do not arbitrarily set every open-shell electron to `m = 0` and present the result as the exact physical ground state.
- Use the most suitable term-aware method available for quantitative visualization.
- Where the selected method produces only an averaged density, label it as an averaged density, not a unique oriented orbital state.

If term-resolved information is not available or the method does not support it, say so.

## 3.6 Relativistic heavy atoms

For heavy and superheavy elements, non-relativistic Slater-screened shapes must not be presented as quantitatively accurate.

Investigate appropriate relativistic atomic-structure methods, including when relevant:

- Dirac–Fock / Dirac–Coulomb.
- Multiconfiguration Dirac–Hartree–Fock (MCDHF).
- Relativistic Configuration Interaction (RCI).
- Breit interaction.
- Finite nuclear-size models (e.g. Fermi nuclear charge distribution).
- QED corrections where physically relevant and supported.
- Spin-orbit and fine-structure effects.

Do not claim these corrections are implemented unless a real calculation or validated dataset exists.

# 4. AUTONOMOUS SCIENTIFIC METHOD AND ENGINE SELECTION

You are authorized to inspect, install, run, and integrate established open scientific software when it gives a demonstrable advantage over a quick custom approximation.

Do not assume that PySCF is the best tool for every element or every observable. Do not assume that a more complicated software package automatically yields a more accurate result.

## 4.1 Candidate engines to evaluate

Evaluate actual capabilities, version, licensing, supported elements, basis sets, atomic-state support, relativistic options, install/build burden, reproducibility, and data-export options for suitable tools. Examples to investigate include:

- PySCF (HF/ROHF/UHF, DFT, selected multiconfigurational and relativistic options where actually supported).
- GRASP2018 / GRASP2K for MCDHF/RCI atomic calculations.
- ATSP2K / MCHF atomic structure tools.
- DIRAC for relevant relativistic electronic-structure work.
- FAC (Flexible Atomic Code) for suitable relativistic atomic structure and related atomic data.
- Other reputable atomic-structure packages or curated evaluated radial-orbital datasets.

These are candidates, not mandatory dependencies. Verify the exact method and feature support in official documentation and primary methodological publications.

Do not bundle or redistribute a package unless its license permits it. It may be acceptable to provide a documented optional offline data-generation pipeline instead of shipping a large external executable.

## 4.2 Observable-dependent model selection

Model selection must depend on the quantity being visualized:

- Orbital radial function.
- Subshell-resolved density.
- Total electron density.
- Ground-state term.
- Orbital energy.
- Total electronic energy.
- Radial expectation value.
- Relativistic radial contraction.

The best method for total spherical electron density may not provide subshell-resolved orbitals. A total HF density cannot be reverse-labelled as a set of orbital wavefunctions without a mathematically justified decomposition.

## 4.3 Required per-element method registry

Create or improve a data/provider registry that records, for each element and supported observable:

- Provider ID and version.
- Method (e.g. exact hydrogenic, RHF, ROHF, UHF, MCHF, MCDHF, RCI, DFT, or explicitly labelled approximation).
- Hamiltonian.
- Atomic/nuclear model.
- Basis set or radial grid.
- Electronic configuration and term represented.
- Electron-correlation treatment.
- Relativistic treatment.
- SCF or numerical convergence status.
- Source or calculation provenance.
- Numerical validation results.
- Known limitations.
- Accuracy/evidence classification.

Possible evidence labels should be explicit, such as:

- `analytic-exact-within-stated-Hamiltonian`
- `evaluated-reference`
- `computed-and-validated`
- `computed-basis-limited`
- `qualitative-approximation`
- `predicted`
- `unavailable`

Do not assign a single global accuracy label to an element if its different properties have different evidence levels.

## 4.4 No fabricated completion

If an accurate radial orbital/density calculation cannot be obtained for a particular element:

1. Keep the element selectable.
2. Display the best supported representation available.
3. Label the method and limitations prominently.
4. Mark high-accuracy data unavailable for that property.
5. Record the blocker in the accuracy matrix.
6. Do not invent radial arrays, orbital energies, contraction factors, basis-set results, term symbols, or reference values.

The objective is maximum coverage with transparent scientific quality, not false uniformity.

# 6. ATOMIC VISUALIZATION REQUIREMENTS

The main v0.5.0 deliverable is the complete and scientifically interpretable visualization of each selected element.

## 6.1 Periodic table and element navigation

Retain and improve the full 118-element periodic table:

- Standard 18-column layout with lanthanide and actinide rows.
- Clear block and category coding.
- Search by name, symbol, and atomic number.
- Keyboard navigation.
- Selected-element state.
- Clear indication when configuration/property values are predicted or unavailable.
- Responsive layout for desktop and mobile.

## 6.2 Full-atom view

The full-atom view must show all occupied subshell contributions supported by the selected physical model.

For each element:

- Display its electron configuration.
- Display occupied shells and subshells.
- Provide independent subshell visibility controls.
- Provide per-subshell opacity controls.
- Use consistent, documented colors.
- Distinguish density intensity from wavefunction phase.
- Make the active model and confidence/evidence class visible.
- Show total electron count and numerical density integration checks where the model provides them.

Where the model supports a genuine nonspherical state-specific density, visualize that density. Where only a spherical/configuration average exists, render the spherical average and label it as such.

Do not artificially deform a spherical density to make an atom visually attractive.

## 6.3 Single-orbital view

Allow inspection of each physically available occupied subshell/orbital:

- `s`, `p`, `d`, `f`, and higher angular momentum supported by the model.
- Real tesseral harmonics and complex spherical harmonics where appropriate.
- Correct quantum numbers and state labels.
- Correct radial and angular nodes.
- Wavefunction phase signs or complex phase only when the displayed model actually provides a wavefunction.
- If the provider supplies density only, do not invent a wavefunction phase visualization.

A total-density table must not be used to fabricate orbital-specific radial functions.

## 6.4 Open-shell presentation

For open-shell elements, provide a scientifically explicit choice between available representations, such as:

- A term/state-resolved result.
- A spin- or configuration-average result.
- A spherical average.
- An explicitly qualitative independent-electron estimate.

Show which convention is currently active. Do not visually imply a unique spatial orientation when the model represents an ensemble or a rotationally averaged density.

## 6.5 3D renderer

Maintain a high-performance Three.js/WebGL2 renderer.

Improve only where required by the new data/model requirements:

- Efficient GPU point rendering or instancing.
- Typed-array transfers from workers.
- No one-mesh-per-point construction.
- Stable camera framing across elements.
- Cross-section planes (XY, XZ, YZ) with continuous offset control.
- Optional coordinate axes and scale bar.
- Meaningful point-cloud density visualization.
- Correct transparency/depth handling.
- Graceful WebGL2 fallback that preserves analytical panels.
- Memory disposal on element/model changes.

The nucleus marker is a visual locator and is not to scale relative to the atom unless a real scale ratio is explicitly represented. State this in the UI and documentation.

## 6.6 Scale and physical units

Use consistent internal units and explicit conversion boundaries.

- Prefer Bohr radii for atomic calculations where natural.
- Convert to pm/Å/eV only at defined display/data boundaries.
- Show the current unit convention.
- Do not conflate covalent radius, van der Waals radius, ionic radius, radial expectation value, classical turning point, and visualization extent.
- Auto-frame the renderer without changing the underlying physical scale.
- Add a comparison mode only if it preserves a declared common scale.

## 6.7 Radial analysis

For a true orbital radial function use:

`P_r(r) = r² |R_nl(r)|²`

when `R_nl` and angular harmonics are normalized separately.

For a 3D volume density, integrate using the correct volume element and do not introduce a second or missing Jacobian.

Show:

- Radial distribution.
- Radial nodes.
- Mean radius or other moment only when calculated by the selected model.
- Tail probability / integration domain quality where available.
- Units and model label.

For numerical orbitals, calculate expectation values from their numerical radial functions and verify quadrature convergence. Do not reuse an analytic hydrogenic expectation formula for a multi-electron orbital unless mathematically justified by the selected model.

## 6.8 Full density and electron count

For an independent-electron density, the integral of the electron density over space should reproduce the expected electron count within a documented numerical tolerance.

For a configuration-average density, clearly describe the averaging convention. For a term-specific state, use the actual state density if supported.

Never normalize an incorrectly truncated imported density silently to force the electron count. Report the mismatch and reject or mark the dataset invalid.
